# Moe Social UI 视觉升级迭代 1

> **日期**：2026-08-29  
> **状态**：进行中  
> **类型**：Flutter 客户端视觉与体验收束  
> **本轮原则**：先提升现有页面的层级、质感和可用性，不扩展业务边界，不改后端契约。

## 1. 为什么现在做

Moe Social 的功能面已经比较完整，但部分页面仍停留在“能用的基础 UI”阶段：

- 页面之间的视觉语言不够统一，颜色、圆角、间距和按钮形态存在旧实现；
- 首屏信息层级偏平，主要任务和次要入口的区别不够明显；
- 部分页面依赖卡片、说明块和按钮堆叠来表达功能，整体偏“功能展示页”；
- 状态、空态、错误态和按压反馈还没有在所有主路径上形成一致体验；
- 视觉升级与信息架构调整容易混在一起，后续维护时不容易判断哪些是产品决策、哪些只是 UI 调整。

本轮的目标不是重新设计整个 App，而是为现有主路径建立一套可持续迭代的视觉基线。

## 2. 当前产品方向

当前工作树中的一级入口为：

1. **首页**：看动态、发帖、按热门 / 最新 / 关注和话题筛选；
2. **好友**：私信、好友关系和好友申请；
3. **AI 伙伴**：长期陪伴关系首页、聊天和日常延伸；
4. **社区**：兴趣小组和讨论广场；
5. **我的**：个人资料、设置和低频功能。

这五个入口是当前代码的实际形态。产品定位和 IA 文档已同步到这一版本；如果后续决定再次合并入口，应先修改产品决策，再调整代码。

### 2.1 首页：内容优先

- 动态流、Stories、筛选和发帖是首页第一任务；
- Feed 分段从图标胶囊收束为更轻的文字分段；
- 发帖入口固定在筛选栏右侧，作为明确但不抢占内容的主操作；
- 话题标签只承担内容筛选，不再兼任社区入口；
- 首页不再常驻 Companion 状态卡。

### 2.2 Companion：按需出现

- AI 伙伴仍然通过底栏和 Hub 保持稳定入口；
- 只有存在明确待回应状态时，主壳才延迟展示一次提醒 Sheet；
- “稍后”不会打断动态浏览，“去看看”进入已有的 AI 伙伴 Tab；
- AI 伙伴 Tab 内由 Hub 自己表达状态，避免底栏角标和 Hub 提示重复。

### 2.3 模型服务：从说明页转为管理页

- 页面重点改为已配置 Provider 的列表管理；
- 每个服务展示连接状态、主机地址、默认模型和额外模型数量；
- “添加服务”固定在底部，列表为空时使用统一空态；
- 编辑、检测、模型管理和删除流程继续复用原有业务逻辑。

## 3. 视觉基线

### 3.1 用户、任务和气质

| 项目 | 定义 |
|------|------|
| 目标用户 | 想轻松浏览动态、记录心情并建立关系的普通用户 |
| 首要任务 | 看懂当前页面、找到主要动作、顺畅完成一次互动 |
| 视觉气质 | Airy Moe、清透、柔和、轻萌，但不过度装饰 |
| 设计取舍 | 内容和任务优先于装饰；清晰层级优先于“看起来很满” |

### 3.2 统一规则

- 页面背景、卡片表面、描边、文字层级和动效优先使用 `MoeTokens`；
- 页面使用 `surface0 / surface1` 建立层级，避免纯白背景上的孤立卡片；
- 主 CTA 使用品牌渐变或品牌色，次要操作降低对比度；
- 卡片只用于承载一组完整信息，不用卡片包卡片；
- 可点击元素必须有按压、选中或加载反馈；
- 长标题、状态胶囊、模型名称和话题标签必须支持省略、换行或横向滚动；
- 支持 reduced motion，不能让动效成为完成操作的前置等待；
- 空态、加载态、错误态和重试动作使用现有 Moe 组件，不另造平行样式。

具体 Token 和组件约束以 [`docs/DESIGN_SYSTEM.md`](../DESIGN_SYSTEM.md)、`lib/theme/moe_tokens.dart` 和 `.cursor/skills/moe-ui-design/SKILL.md` 为准。

## 4. 本轮范围

### 4.1 纳入范围

- 主壳与底部导航的视觉承载；
- 首页顶栏、Stories、Feed 分段、话题筛选和发帖入口；
- Companion 按需提醒 Sheet；
- Provider 列表、状态胶囊、空态和底部添加入口；
- 「我的 → 设置 → 关于与支持」增加官网入口，使用系统浏览器打开；
- 触及页面的 Token、按压反馈、窄屏布局和无障碍语义；
- 视觉相关的最小 Widget / ViewModel 验证。

### 4.2 明确不做

- 不改后端 API、Proto、数据库和 Provider 契约；
- 不新增 AI 酒馆、多角色大厅或游戏入口；
- 不把视觉升级扩展成全仓页面重写；
- 不因为视觉统一而擅自更换 Provider、路由或状态管理；
- 不把实验能力重新放入普通用户的主路径；
- 不用大面积渐变、装饰性光斑或卡片堆叠替代信息层级。

## 6. 验收标准

### 首页

- 打开首页后，用户第一眼看到的是动态内容和筛选，不是 Companion 配置或说明；
- 发帖只有一个清晰的主入口，点击后能回到原有发布闭环；
- 话题标签看起来是筛选项，不会误认为社区导航；
- 动态列表图片优先服务于浏览密度，点击后再进入完整比例的全屏查看；
- 多图动态不因图片数量线性增长到占满屏幕，详情页媒体也有明确上限；
- Companion 有待回应时才出现提醒，普通浏览不会被打断；
- Feed 加载、空态、错误和重试行为保持可见且可恢复。

### 主导航

- 五个入口在窄屏不溢出、不挤压文案；
- AI 伙伴角标、Hub 状态和聊天已读之间的职责清晰；
- 社区作为一级入口时，首页与社区仍保持“算法 / 关注流”和“兴趣 / 讨论广场”的边界。

### Provider

- 有服务时可以快速比较名称、连接状态、主机和默认模型；
- 无服务时空态文案明确，底部“添加服务”始终可达；
- 编辑、检测、模型管理和删除不改变原有服务契约；
- 连接失败不能伪装成成功或空数据。

### 工程

- 改动页面不直接发 HTTP 请求；
- 新增视觉参数优先进入 `MoeTokens`；
- `flutter analyze` 无 error，相关测试通过；
- 本轮不产生后端生成文件、数据库迁移或 API 契约变更。

## 7. 已知风险与后续债务

- 首页已经没有 Companion 卡片，但 `HomeFeedViewModel` 仍保留 Companion snapshot、identity 和相关刷新请求；后续应确认这些数据是否仍被创建动态、评论或其他深链复用，确认无消费者后再移除，避免无意义请求；
- 主壳提醒目前按 `_selectedIndex == 0` 判断是否在首页，二级路由覆盖场景仍需手动验证；
- Provider 页面仍有历史视觉债务，尤其是编辑 Sheet 内的硬编码颜色、字号、圆角和动画时长，本轮只收束了列表页，不做整页重写；
- 当前缺少主壳、提醒 Sheet 和 Provider 列表的专门 Widget 测试，视觉调整完成后需要补上最小回归覆盖。
