# 用户级记忆统一改造验收脚本

> **架构 SSOT**：[用户记忆系统-OpenClaw式演进设计.md](./用户记忆系统-OpenClaw式演进设计.md)  
> **监控台**：[memory-system-dashboard.html](./memory-system-dashboard.html) · [docs/index.html](../index.html)

## 1. 目标

验证“后端用户记忆单一事实源 + Web 可用 + 模型切换不失忆 + raw 调试边界可见”是否真正落地；并覆盖 **混合检索** 与 **设备/记忆分离**。

## 2. 验收前准备

1. 使用同一账号登录 App/Web。  
2. 确认 `AI 模型配置` 页面里 `终端同款模式=已关闭`。  
3. 确认聊天接口显示为 `/api/llm/chat`。  
4. 选择一个模型 A（例如 `llama3:8b`）。  

## 3. E2E 脚本

### Case A：基础记忆命中

1. 在聊天中输入：`我叫小萌，我喜欢画画和爵士乐。`  
2. 再输入：`你记得我刚刚说了什么偏好吗？`  
3. 期望：回答中命中“画画/爵士乐”偏好，且语义正确。  

### Case B：模型切换后不失忆

1. 切换到模型 B。  
2. 输入：`你还记得我的爱好吗？`  
3. 期望：仍能命中同一用户偏好，不出现“重新认识你”的回答。  

### Case C：反馈后 1-2 轮生效

1. 打开 `模型记忆线`，找到相关记忆项。  
2. 对一条记忆执行 `correct`，例如把“爵士乐”改为“古典乐”。  
3. 返回聊天，输入：`我的音乐偏好是什么？`（连续 1-2 轮）  
4. 期望：回答逐步稳定为“古典乐”；旧偏好不再高频出现。  

### Case D：Web 端可用

1. 在 Web 端重复 Case A/B。  
2. 点击聊天页 `记忆库` 入口。  
3. 期望：可进入后端记忆线页面并看到同账号记忆。  

### Case D2：聊天页不走本地记忆链路

1. 在移动端与 Web 端分别发起同主题对话。  
2. 确认两端回答都依赖同一账号记忆，不因本地 SQLite 差异出现不同“人设”。  
3. 期望：聊天页仅依赖后端记忆注入链路，本地记忆变化不影响主聊天行为。  

### Case E：raw 调试边界

1. 开启 `raw 调试模式`。  
2. 聊天一轮后观察回答（允许出现记忆不命中）。  
3. 打开 `AI 模型配置` 页，确认显示 `服务端记忆是否生效=否（raw 调试）`。  
4. 关闭 raw 模式后再测一轮，期望恢复服务端记忆命中。  

### Case F：桥接异常可提示

1. 人为让后端无法连接 Ollama（例如停掉本地 Ollama）。  
2. 发起聊天或点击连接测试。  
3. 期望：前端出现明确错误提示，不是静默失败。  

### Case G：混合检索（Phase 2）— ✗ **整节已下线，无法执行（2026-09-11 实测）**

> 向量/Embedding 记忆系统已于 2026-06-29 随 `backend/pkg/memory/` 整体删除，本节四个步骤**每一步都会失败**，且失败点比「配置没生效」更深：
>
> - **第 2、3 步的路由没有实现**：`POST /api/user/{id}/memories/reindex` 与 `GET /api/user/{id}/memories/search` 虽在 `llm_messages.proto:295-303` 声明、并由生成的 `llm_messages_http.pb.go:65-66` 挂上路由，但 `http_proto.go:183` 注册的 `protohttp/llm.Server` 内嵌 `UnimplementedLlmChatServer`，**只实现了 `GetAiUserConfig` / `UpsertAiUserConfig` 两个方法**（`internal/server` 与 `internal/service` 下 `memories` 零命中）→ 实际返回 `codes.Unimplemented: method SearchUserMemories not implemented`。
> - **第 4 步的开关是死键**：`memory.search.hybrid_enabled` **零读者**（`pkg/conf/config.go:20` 已把 `memory.search.*` 整段记名为死配置），改它不会有任何效果。
> - **不是待修 bug**：Flutter 与 moe-admin 均无调用方（Flutter 里的 `memories` 命中的是 companion 记忆，属另一套子系统）。这是删除向量记忆后残留的**死接口面**。
> - 要恢复需先决策：清理 proto（连带删掉 `RebuildUserMemoryEmbeddings` / `SearchUserMemories` 两个 rpc 与相关 message），还是重新实现。详见 [用户记忆系统-OpenClaw式演进设计.md](./用户记忆系统-OpenClaw式演进设计.md) 顶部横幅。

### Case H：设备与记忆分离 — ⚠️ **第 1、3 步同样打在未实现的路由上**

> `POST` / `GET` / `DELETE /api/user/:id/memories` 三条路由由 `llm_messages_http.pb.go:59-61` 挂到内嵌的
> `UnimplementedLlmChatServer`（同 Case G 的成因），因此第 1、3 步会返回 `codes.Unimplemented`。
> 只有第 2 步的 `/api/user/:id/devices` 属 **user 域**（`user_messages.proto:799,804`）、是另一套实现，仍可验证。

1. ✗ `GET /api/user/:id/memories` 列表中不应出现 `device_info:*` 作为用户记忆展示项。  
2. ✅ `GET /api/user/:id/devices` 可返回当前账号设备登记。  
3. ✗ `POST /memories` 且 `source=device_sync` 应被拒绝。  

### Case I：记忆工具 list 过滤（路径 B，可选）

1. Provider 开启「支持 tool_calls」。  
2. 模型调用 `memory_list`，参数 `query=咖啡`，期望返回与 search 相近的子集。  

## 4. 指标口径（观察期）

### 4.1 记忆命中率

- 定义：命中记忆的回答轮次 / 总回答轮次。  
- 建议窗口：按用户近 50 轮统计。  

### 4.2 误提率

- 定义：被用户 reject/correct 的记忆条数 / 新提取记忆条数。  

### 4.3 冲突率

- 定义：同一 `user_id + key` 在 24h 内发生值冲突的比例。  

### 4.4 反馈采纳率

- 定义：反馈后 1-2 轮内回答行为变化达成的比例。  
- 判定：可由人工抽样或规则匹配（关键词命中）评估。  

### 4.5 注入 token 成本

- 定义：记忆注入文本估算 token / 轮。  
- 目标：在命中率提升前提下，保持成本稳定或下降。  

## 5. 通过标准

1. Case A/B/C/D/E/F 全部通过。  
2. 反馈采纳率达到可用阈值（建议 >= 70%）。  
3. 命中率提升趋势明显，误提率可控且逐周下降。  

## 6. 当前已知待收敛项

1. `MemoryManagerPage` 仍保留本地 SQLite 画像/配置链路，需要迁移到后端来源。  
2. 大用户记忆列表仍建议补充分页/limit 与后端查询观测。
