# 扫码与二维码功能开发需求（持续优化）

## 1. 背景

当前项目已具备：

1. 个人二维码生成与展示。  
2. 相机扫码与相册识别。  
3. 联系人二维码识别后发起加好友请求。  

为支撑后续扩展（群组、活动、深链、设备绑定等），需要把扫码与二维码能力升级为“可扩展协议 + 可路由处理”的基础设施。

---

## 2. 本轮已完成（2026-05-09）

### 2.1 统一二维码协议（优化建议 #1）

已完成统一结构：

```json
{
  "version": 1,
  "type": "contact",
  "timestamp": 1715250000000,
  "payload": {
    "userId": "123",
    "username": "xxx",
    "avatar": "...",
    "moeNo": "1000000001"
  }
}
```

兼容策略：

1. 扫码解析层仍兼容历史扁平结构（`type/userId/username/...`）。  
2. 生成端默认输出新结构。  

### 2.2 扫码分发层（优化建议 #2）

已在扫码页面实现按 `type` 的路由分发：

1. `contact` -> 联系人加好友流程。  
2. `unknown` -> 明确提示“暂不支持该二维码类型”。  

这为后续新增码类型提供统一扩展点，避免把全部逻辑堆在一个函数里。

---

## 3. 后续待做（来自上一轮建议）

### 3.1 安全校验增强（优化建议 #3）

目标：

1. 增加二维码签名/验签（防伪造）。  
2. 增加时间戳有效期校验（防重放）。  
3. 敏感业务码支持一次性 token。  

验收：

1. 篡改 payload 后不可通过验签。  
2. 过期码会被明确拒绝并提示。  

### 3.2 业务扩展能力（优化建议 #4）

计划新增类型（按优先级）：

1. `group_invite`（群聊邀请）。  
2. `event_invite`（活动/任务邀请）。  
3. `deep_link`（页面直达）。  
4. `device_bind`（设备绑定场景）。  

验收：

1. 各 type 有独立 handler。  
2. 新增 type 不修改核心扫码主流程。  

### 3.3 体验增强（优化建议 #5）

目标：

1. 扫码历史记录（本地）。  
2. 重复扫码识别提示。  
3. 失败原因可解释（格式错误/不支持/过期/权限不足）。  
4. 成功动作二次确认与撤销入口。  

---

## 4. 定位与天气联动专项（新增）

现状问题：

1. 城市展示与定位变化不同步。  
2. 天气有时不随城市变化刷新。  

本轮策略：

1. 天气接口切换为免费 API（城市维度查询）。  
2. 通过定位坐标先反解城市，再按城市查询天气。  
3. 增加城市名规范化（去除“市/区/县”等后缀）与缓存键统一。  

后续优化：

1. 增加天气接口降级策略（主接口失败 -> 备用接口）。  
2. 增加城市手动切换入口（用户可覆盖定位城市）。  
3. 增加天气缓存可视化（最后刷新时间）。  

---

## 5. 里程碑建议

1. M1（已完成）：统一协议 + 扫码分发。  
2. M2：签名校验与过期校验。  
3. M3：群组/活动二维码落地。  
4. M4：扫码历史与失败诊断增强。
