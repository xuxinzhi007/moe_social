# Moe Social 可用性升级计划

## 背景

Moe Social 的正式定位是萌系心情社交，核心是发动态、浏览互动、建立关系；AI 伙伴是增强能力，不是工具箱或游戏大厅。当前实现已经覆盖功能面，但要从演示型产品进入可用产品，应优先提升主路径可靠性、信息架构一致性和环境可达性，而不是继续叠加实验功能。

## 调研与证据

### 仓库内产品证据

- `docs/product/product-positioning.md` 将动态流、发帖、评论点赞、好友和私信定义为 P0。
- `docs/dev/p0-adjustment-backlog-2026-06-03.md` 已将首页、消息、AI、我的主线与三态、草稿、重连列为收口标准。
- `lib/pages/feed/home_page.dart` 和 `lib/pages/chat/conversations_page.dart` 已有加载、空、错和重试基础，后续应复用，而不是另造页面框架。
- 主路径页面仍存在多处超长文件，例如 `companion_chat_page.dart`、`create_post_page.dart`、`comments_page.dart` 和私信相关页面；改动应按可测试的 UI/状态边界拆分。
- `lib/utils/config.dart` 默认使用本地环境，公开安装包若未切换环境会连接私网地址；这是发布前必须关闭的可达性风险。

### 市场启发（待补可引用外部来源）

当前运行环境禁止访问外部网页，无法在本轮验证实时竞品资料。后续每个功能切片开始前，需补至少一个可访问的一手来源或公开产品观察记录。先采用已稳定的产品启发作为假设，而不是事实宣称：

1. 社交产品的首屏任务应是消费内容或发布内容，次级能力不能抢占首屏。
2. 私信应让用户快速知道“谁在等我、我能回复什么”，离线、失败和重连必须显性。
3. 创作流程应保证草稿、上传进度、失败恢复和发布后回流，不让用户重复劳动。
4. 设置和开发工具不应干扰普通用户；实验功能必须由 Flag 关闭入口与路由。

## 目标与非目标

### 本阶段目标

1. 让首次打开、浏览动态、发帖、私信四条基础动作在真实网络环境下可理解、可恢复、可验证。
2. 收束重复入口和实验功能，减少“功能堆叠”的演示感。
3. 将新增 UI 和状态逻辑维持在 `pages → provider/viewmodel → service` 边界内。
4. 为每个改动建立验收条件、回滚开关和最小验证。

### 非目标

- 不新增游戏大厅、第三方游戏联机或无明确价值的 AI 工具。
- 不全仓替换 Provider、路由或设计系统。
- 不在未经部署验证的情况下切换生产 API 地址或修改服务端密钥。

## 执行门禁

每个新切片执行前必须完成：

1. **问题证据**：来自用户反馈、日志、测试或现有实现，不凭感觉改 UI。
2. **市场/产品研究**：至少一条一手来源、竞品实际流程观察或内部产品 SSOT；若外网不可访问，明确记录缺口。
3. **单一任务**：写清用户任务、成功条件、失败状态和不做什么。
4. **影响评估**：确认路由、FeatureFlag、服务契约、缓存和兼容性影响。
5. **验证与回滚**：先列定向测试/冒烟路径；可见入口变更必须可由 Flag 或回退路径撤销。

### 用户体验优先级

除非某项服务端工作直接消除用户可见的失败、等待或数据丢失，否则不应优先于主路径体验。每个切片先回答：

1. 用户是否能看懂当前状态（加载、离线、失败、成功）？
2. 用户失败后是否能保留输入并直接重试？
3. 同一目标是否存在多余并列入口？
4. 模拟器或真机是否能看到预期反馈？

### Android 主路径审计（2026-08-21）

- 首页首屏可直接看到动态、筛选和唯一的“发动态”操作。
- 好友页无会话时保留“去通讯录”主引导，顶部“添加好友”为唯一新增好友入口；移除空态内重复 CTA。
- 启动日志曾显示每日自动签到读取了 Provider 作用域外的 context，导致用户错过签到与等级刷新；已改为 navigatorKey 上下文调度，模拟器重启日志不再出现该错误。
- 实时私信、断网恢复、图片慢传和实际发送失败仍需在双账号真机环境完成验收，不能只依赖静态测试。

## 优先级路线

| 优先级 | 切片 | 用户价值 | 验收 |
|---|---|---|---|
| P0-A | 环境与启动可达性审计 | 安装后能连到正确服务，不把私网配置带入发布包 | 真机/模拟器启动时展示正确环境，登录和首页请求可达 |
| P0-B | 动态流可靠性 | 浏览、刷新、分页、空态和错误重试连贯 | 网络失败后可重试；重复请求不重复插入；发布后回流正确 |
| P0-C | 发帖恢复闭环 | 输入、素材、草稿和发布失败不丢失 | 中断后恢复草稿；上传/发布错误明确且可继续操作 |
| P0-D | 私信可靠性 | 未读、断线、重连、发送失败可见 | 断网和恢复网络后状态正确；失败消息可重试 |
| P0-E | 个人资料可信度 | 明细失败不伪装成零数据，用户能直接刷新 | 断网时保留旧资料并显示待刷新；恢复后刷新成功消失 |
| P0-F | 调试包启动可达性 | 调试或登录时不被无效的正式版更新弹窗阻断 | debug 首次启动不弹更新；设置页手动检查仍可用 |
| P0-G | AI 社区身份恢复 | 历史伙伴身份可恢复，不向用户暴露 500 技术错误 | 旧 bot 键变化后自动重绑；普通同名用户不被接管 |
| P0-H | 首屏启动反馈 | 不让非必要 SDK 阻塞首个可交互页面 | Dev 冷启动直接显示首屏；微信授权仍可完成注册 |
| P1 | 页面瘦身与复用 | 降低维护风险、保证后续迭代速度 | 超长页按 UI/VM 边界拆分且行为测试不回归 |
| P1 | 实验入口治理 | 普通用户只看到与社交相关能力 | Flag 关闭时无可见入口且路由不可用 |

## 首个实现切片

### P0-A：构建环境与启动基址

**问题证据：** 发布前必须确认安装包使用正确 API 基址；当前项目由 `lib/utils/config.dart` 中的 `AppConfig.isProduction` 和两个基址常量手动控制。

**产品研究：** 仓库的产品定位和发版速查都要求安装包可直接使用线上服务。外部 Android 文档在受控浏览环境中超时，未绕过访问策略；本切片不将未核验的外部结论作为依据。

**实现与回滚：** 按项目维护者要求，继续采用手动 `isProduction = false/true` 切换；不引入构建变量、CI 覆盖或启动时远程重写地址。回滚只需改回对应布尔值，不涉及数据库与后端契约。

**已验证：** 默认本地环境的配置单测与定向 `flutter analyze` 通过。发布前必须由维护者手动将该值切到线上，并完成真机验证。

**待验收：** 在真实 Android 设备上安装线上构建，确认启动日志、登录与首页请求实际到达部署服务；同时确认公网 API 的 TLS、CORS 与 `/api/public/client-config` 响应。未经此验收不得宣称线上服务已可用。

### P0-B：动态流请求一致性

**问题证据：** `HomeFeedViewModel.loadMorePosts` 以前直接拼接下一页，后端分页在发布、删除或排序变化时出现重叠会渲染重复卡片；切换 Feed 模式时，已发出的旧请求没有版本校验，返回顺序反转时可能以旧结果覆盖新筛选。

**产品研究：** 产品 SSOT 将“浏览互动”列为冻结主路径，成功标准包含刷新、分页、空态和错误重试的连贯体验。外部公开竞品页面在本环境的访问仍受限，本切片仅基于可复现的客户端状态竞态与仓库产品证据实现，不作未经验证的竞品事实陈述。

**实现与非目标：** ViewModel 为每个筛选状态记录请求版本，丢弃过期响应；分页和首屏按帖子 ID 去重，并通过注入的域服务加载器测试状态机。没有修改页面路由、UI、后端接口或点赞/评论逻辑。

**已验证：** 覆盖“重叠分页去重”和“切换模式后旧响应不覆盖新列表”的两项单测；定向 `flutter analyze` 通过。后续真机验收应包含连续下拉、快速切换热门/最新/关注，以及断网后的重试提示。

### P0-C：发帖草稿恢复

**问题证据：** 草稿此前仅在页面 `dispose` 时异步写入；系统回收或意外退出可能丢失刚编辑的内容。并且发布成功清除草稿后，页面销毁会无条件再次保存同一内容，导致已发布内容被错误恢复为草稿。

**产品研究：** 产品 SSOT 的“记录心情”主路径要求中断后恢复草稿、发布失败后可继续操作。外部实时竞品资料仍无法在当前受控浏览环境中核验，因此只以该可复现的恢复链路问题作为本切片依据。

**实现与非目标：** 常规发帖页在文字、图片、话题、心情或手绘变更后 700ms 防抖保存，发布前再次落盘；发布成功取消待执行保存，且只在存在未保存变更时的销毁阶段兜底。编辑模式与群组发帖继续不使用本地草稿；未改变发布 API、上传策略或 UI 信息架构。

**已验证：** 新增草稿完整字段恢复与清理行为单测，发帖页、ViewModel 与测试定向 `flutter analyze` 通过。待真机验证：输入后强制结束 App、发布失败后重开、发布成功后重开均应分别恢复未发布草稿、保留编辑内容、且不恢复已发布内容。

### P0-D：私信连接与发送状态

**问题证据：** 聊天页通过 `ChatPushService.connectionLive` 显示“连接中断，正在重连”，但服务此前在创建 WebSocket Channel 后立即标为已连接，握手失败时会短暂隐藏断线提示。图片消息上传成功后也会过早解除发送锁，服务端消息写入尚未完成时允许再次发送。

**产品研究：** 产品 SSOT 将“建立关系”定义为冻结主路径，Flutter 产品规范要求私信自动重连、断线和发送失败均用户可见。受控浏览环境无法核验外部实时竞品流程；本切片只以聊天页的实际状态机和可见提示为依据。

**实现与非目标：** 共享 Chat WS 在 `WebSocketChannel.ready` 握手成功后才报连接可用，并在失败时沿用现有指数退避；图片发送从上传到服务端确认都保持发送中。文字发送失败会恢复到输入框并提示可直接重试，避免用户重新输入。未修改私信协议、后端契约、页面入口或消息存储格式。

**已验证：** `dart analyze` 覆盖 WS 服务、聊天 ViewModel 和页面，无错误；`git diff --check` 通过。待真机验证：飞行模式切换后断线条出现并在握手成功后消失；慢网图片发送期间发送按钮保持禁用；上传或发送失败显示错误且不遗留乐观消息，文字失败后可直接再次发送。

### P0-E：个人资料明细可信度

**问题证据：** `ProfilePage` 之前对关注、粉丝、动态、会员和徽章等明细请求单独吞掉异常并回退为 `0`；网络失败时用户会把未加载到的值误认为真实的空数据，且没有可见刷新入口。

**产品研究：** Material Design 3 的 [Progress indicators guidelines](https://m3.material.io/components/progress-indicators/guidelines) 将进度状态定义为帮助用户理解正在进行过程的反馈。本切片沿用这一原则：明细刷新期间保留已知数据并显示进度；失败则显式标记为“资料待刷新”，而不是以零值伪装成功状态。

**实现与非目标：** 每项明细加载携带成功标记；失败项不覆盖已有资料，任意一项失败会在个人页标题旁显示“资料待刷新”，并提供“刷新资料明细”按钮。未修改资料 API、缓存、路由或数据库；首次无缓存且全部失败时，统计仍为默认值，但待刷新状态会明确说明其不可信。

**已验证：** `dart format lib/pages/profile/profile_page.dart`、`dart analyze lib/pages/profile/profile_page.dart` 与 `git diff --check` 通过。待真机验收：先正常加载资料，再断网下拉或点击刷新，应保留旧统计并显示待刷新；恢复网络后点击刷新，提示消失且数据更新。

### P0-F：调试包启动更新不阻断

**问题证据：** Android 模拟器安装 debug APK 后，主界面启动自动检查命中远端正式版 `v1.0.9`，立即弹出更新框并遮住登录页面。弹窗同时提示 debug 与正式签名不能覆盖安装，说明该自动提示没有可执行价值，却阻断了调试和首次使用。

**产品研究：** 仓库 `MainPage` 已明确要求更新检查放在主界面就绪后，避免抢占登录/闪屏。尝试访问 Android 官方 In-app Updates 指南时请求超时，未绕过访问限制；因此不作未核验的外部结论。本切片遵循现有产品约束：无效更新提示不得打断主路径。

**实现与非目标：** `StartupUpdateService` 在 `kDebugMode` 下直接跳过自动检查；设置页的手动“检查更新”保持原行为，便于验证发布配置。正式包的启动检查、强制更新、冷却和“稍后更新”记录均不变；未改动版本接口或发布配置。

**已验证：** 定向静态分析与 debug APK 构建后安装启动通过；启动日志不再进入自动检查路径。待验收：真机 debug 首次启动直接到登录/首页，设置页手动检查仍可打开更新信息；release 包仍按远端强制/软更新策略执行。

### P0-G：AI 社区身份恢复

**问题证据：** Android Dev 包日志复现 `GET /api/companion/community-identity` 返回 500：历史 bot 用户名 `bot_c_1` 已存在，但伙伴 Agent ID 改变后代码仅按新 Agent 查找，再以同一用户名创建 bot，触发 `users.idx_users_username` 唯一键冲突。

**产品研究：** Material Design 3 的 [Dialogs guidelines](https://m3.material.io/components/dialogs/guidelines) 指出弹窗应用于需要用户处理的重要提示。本故障是系统可自动恢复的历史映射问题，不应将数据库技术错误抛给用户或要求用户处理；服务端应幂等恢复身份，客户端继续使用原契约。

**实现与非目标：** 先按当前 Agent 查找；未命中时仅查找 `is_bot=true` 且匹配该房主稳定用户名或 bot 邮箱的历史账号，找到后更新其 `bot_agent_key` 并复用。普通同名用户不会被查询或更新；未改变 API、用户表结构、客户端入口或配置。

**已验证：** SQLite 单测覆盖“历史 bot 自动重绑”与“普通同名用户不被接管”；`go test ./internal/service/companion/...`、`go test ./internal/server/protohttp/companion/...` 通过。待验收：重启本地后端后，以原账号访问首页或 AI 伙伴页，`community-identity` 应返回 200 且不再出现该唯一键冲突。

### P0-H：首屏启动反馈与微信 SDK 按需初始化

**问题证据：** Android Dev 包启动日志显示 `WechatSdkService.ensureRegistered()` 约耗时 8.6 秒；其间首屏一度显示纯白画面。移除该预注册后，启动任务约 1.8 秒结束，但 Flutter 首帧前 Android 的 `launch_background` 仍是纯白，因此慢设备或插件加载期依然会呈现白屏。微信服务在授权按钮点击时已由 `requestAuthCode()` 调用 `ensureRegistered()`，故不属于首屏必需条件。

**产品研究：** 尝试访问 Android 官方启动性能文档时请求超时，未绕过访问限制。仓库 `StartupManager` 的设计已区分关键与后台任务，产品原则是先让用户看到并操作首屏，再延迟非必要能力；本切片仅将微信 SDK 恢复为按需初始化。

**实现与非目标：** 从启动任务队列移除微信 SDK 注册；微信登录按钮仍通过原有 `requestAuthCode()` 按需注册，因此授权契约不变。Android 原生启动背景改为与 Flutter Splash 一致的紫色星标，并将运行期窗口背景保持为同色，覆盖 Flutter 首帧前的空白窗口。未调整 API、登录表单、通知初始化、环境配置或微信 SDK 参数。

**已验证：** `flutter build apk --debug` 与 `git diff --check` 通过。已在 `emulator-5554` 安装 Dev 包并强制冷启动：约 5 秒截图显示紫色星标原生启动屏，约 17 秒截图可进入首页，未出现纯白等待。受当前 Android 编译 SDK 限制，未直接引用 Android 12 专用 `Theme.SplashScreen`，因此保持所有已支持 API 均可构建的资源实现。待真机验收：点击微信登录时仍应注册 SDK 并继续原授权流程。回滚只需恢复白色 `launch_background` 与微信启动任务。

## 影响范围

- Flutter：`lib/main.dart`、`lib/services/api_service.dart`、`lib/utils/config.dart`、启动与设置相关 UI。
- 后端：仅在确定公开 API、TLS、CORS 与配置契约后才改动。
- 文档：环境配置和每个已完成切片的验证记录。

## 回滚

- UI 切片通过 FeatureFlag 或保留原路由进行回退。
- 环境切换不修改数据库；配置改动保留可切换的开发/线上值，并在真实设备验证后发布。
