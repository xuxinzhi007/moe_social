## 1. 背景与目标

当前项目已接入 Ollama，并具备基础对话、模型管理、记忆提取与画像整理能力。  
但整体实现仍偏“可用 Demo”，距离“懂用户、会学习、可持续训练”的产品目标有明显差距。

目标定义：

- 实现 **用户级长期记忆**：能稳定记住用户偏好、习惯、重要事实和长期计划。
- 实现 **持续学习**：对每轮对话进行结构化吸收，自动更新记忆而非简单堆积。
- 实现 **可训练能力**：支持把用户反馈与高质量样本沉淀为可复用训练/微调数据。
- 实现 **可控可审计**：记忆可查看、可编辑、可删除，可追溯来源与更新时间。

## 2. 当前缺陷清单（按优先级）

> 进度说明（2026-05-08）：V1 已完成一部分后端优化，以下清单包含“仍未完成”与“已部分缓解”状态。

## P0（高优先级，影响安全/稳定）

- LLM 管理接口鉴权不足（下载模型、删除模型、创建模型、聊天等存在被滥用风险）。
- “停止生成”仅停前端状态，未真正中断后端推理，请求仍可能继续消耗资源。
- 流式交互名义上启用 `stream`，但前端仍是整包等待，无法实现真实增量输出。

## P1（中优先级，影响效果与体验）

- 记忆提取并发治理不足：后台异步提取缺少队列/限流，压力场景下易堆积。
- 记忆日志存在敏感信息泄露风险：原始提取结果直接打印，不利于隐私合规。（已部分缓解：聊天记忆相关日志已收敛为计数/长度）
- 记忆配置存在“名义字段未生效”问题（部分参数未真正参与调度触发）。
- 筛选与排序等辅助功能逻辑不完整，影响智能体管理体验。

## P2（低优先级，影响可维护性）

- 会话与使用统计部分仍为本地临时态，跨设备与重启后连续性较弱。
- 局部页面状态更新粒度较粗，长会话下渲染性能有优化空间。
- 部分空安全和异常处理路径仍可进一步收敛。

## 3. 目标能力拆解（你要的“懂用户 AI”）

为实现“记住用户爱好、理解操作/对话习惯、持续学习并支持训练”，建议按四层能力建设：

1. **记忆采集层**  
   - 对每轮对话提取结构化事实（偏好、禁忌、计划、关系、风格）。
   - 支持冲突检测（新旧事实矛盾时更新而非叠加）。

2. **记忆治理层**  
   - 去重、合并、过期、可信度评分、来源追踪（来源会话+消息 ID）。
   - 用户可视化管理：查看/修订/删除/冻结某条记忆。

3. **推理注入层**  
   - 根据场景注入最相关记忆（而非全量注入），控制 token 成本与噪声。
   - 注入策略可配：仅画像、画像+高优先级事实、任务型临时记忆等。

4. **训练闭环层**  
   - 把用户正反馈（点赞、采纳、复制）和人工修订沉淀为偏好样本。
   - 形成监督数据集（SFT/DPO 候选），支持周期化离线训练或蒸馏。

## 4. 推荐演进路线图

## Phase 1：安全与稳定基线（1 周）

- 为 `/api/llm/*` 与 `/api/llm/*/raw` 增加鉴权与限流。
- 打通真正的可取消链路（前端取消 -> 后端 context cancel -> Ollama 中断）。
- 改造成真实流式输出（SSE/NDJSON 增量渲染）。
- 统一错误码与超时重试策略，避免前后端语义不一致。

验收标准：

- 未授权无法操作模型管理接口。
- 停止生成后，后端请求能在秒级中止。
- 首字延迟与整段返回差异可观测。

## Phase 2：用户级记忆 MVP（1-2 周）

- 记忆数据模型升级：`user_id + memory_type + confidence + source + updated_at`。
- 建立冲突更新规则（例如偏好反转、计划变更、关系变更）。
- 记忆提取任务队列化（串行/限并发），降低高峰期不稳定。
- 提供记忆管理页面（查看、编辑、删除、锁定、忽略）。

验收标准：

- 同一用户多轮对话后，偏好命中率明显提升。
- 错误提取可人工纠正且不会重复污染。

## Phase 3：画像与长期学习（2 周）

- 基于原始记忆自动整理用户画像（身份、兴趣、表达风格、目标）。
- 建立“记忆衰减 + 强化”机制（高频被验证信息权重提升）。
- 引入反馈信号：用户评分、编辑、复制、追问作为学习依据。

验收标准：

- AI 回答更稳定地体现用户偏好，减少重复追问。
- 画像能解释“为什么给出这个回答”（可审计）。

## Phase 4：训练能力（持续演进）

- 样本集管道：对话 -> 清洗 -> 标注 -> 训练集版本化。
- 训练策略：先 LoRA/蒸馏，再按业务效果评估迭代。
- 加入 A/B 实验框架，比较“基础模型 vs 记忆增强 vs 训练增强”。

验收标准：

- 关键指标持续提升（满意度、任务完成率、复访对话时长）。

---

## 5. 关键技术建议

- 记忆分层：`短期上下文`、`长期事实`、`画像摘要` 分开存储与注入。
- 记忆检索：优先按语义相关度 + 时间衰减 + 重要性综合排序。
- 隐私治理：日志脱敏、敏感字段加密、用户级导出/删除能力。
- 观测体系：记录命中率、误提率、冲突率、注入 token 成本、延迟。

---

## 6. 风险与规避

- **风险：记忆污染**（错误提取导致越聊越偏）  
  规避：引入置信度阈值 + 人工可修订 + 冲突回滚。

- **风险：成本失控**（全量注入导致 token 暴涨）  
  规避：相关性召回 + 注入上限 + 摘要缓存。

- **风险：隐私合规问题**  
  规避：敏感信息分级存储、最小化日志、用户可删除与可追溯。

---

## 7. 下一步执行建议（可直接开工）

1. 先做 Phase 1（安全+真实流式+可取消），这是所有后续能力的地基。  
2. 并行推进 Phase 2 的记忆模型升级与管理页，确保“可纠错”。  
3. 上线一版小流量灰度，先验证记忆命中率和误提率。  
4. 指标稳定后再推进训练闭环，避免“坏数据训练坏模型”。

## 8. 成功标准（产品视角）

当用户在多天后再次进入对话，AI 能自然记住并使用以下信息，即可视为阶段成功：

- 用户长期偏好（喜欢/不喜欢、风格、语气）。
- 用户长期目标（学习、工作、计划）。
- 用户稳定习惯（时间偏好、表达方式、常用任务）。
- 用户显式反馈（“这次回答好/不好”）能影响后续行为。

## 9. 后端第一版（V1）落地范围

本次先做“不改动数据库结构的后端第一版”，基于现有 `user_memories` 数据直接提升效果与稳定性。

V1 目标：

- 在不增加训练成本的前提下，让小模型在有限上下文里“更像懂用户”。
- 避免把全部历史记忆硬塞进 prompt，减少噪声与 token 浪费。

V1 改动点（后端）：

1. **相关记忆召回注入**  
   - 从 `GetUserMemories` 返回集合中按“最近性 + 关键词命中”打分。  
   - 仅注入 TopN（如 8 条）记忆，替代“全量注入”。

2. **注入上限控制**  
   - 对注入条数和总字符数设置硬上限，避免挤占对话上下文预算。  
   - 当无明显命中时，回退注入少量最近记忆，保证鲁棒性。

3. **记忆去重与清洗**  
   - 对重复 key/value、空值、噪声值进行过滤。  
   - 避免 system prompt 中出现重复语义。

4. **敏感日志收敛**  
   - 移除“原始记忆提取内容”直接打印，改为计数与长度日志。  
   - 降低隐私泄露风险。

V1 当前实现状态（已落地）：

- 已完成相关记忆召回：按“最近性 + 关键词命中”打分，并在命中场景按上限注入。
- 已完成注入预算：条数上限与字符上限生效，避免全量历史挤占上下文。
- 已完成无命中回退策略：无明显命中时仅注入少量最近记忆（避免噪声和 token 浪费）。
- 已完成去重与噪声过滤：重复记忆、空值、占位噪声值会被过滤。
- 已完成敏感日志收敛：不再输出原始记忆文本，改为统计信息。

V1 非目标（后续 Phase 2 处理）：

- 不做表结构升级（`confidence/source/feedback` 等先不入库）。
- 不做训练/微调流水线。
- 不做跨设备全局记忆合并策略（本轮仅明确方案，不做表结构改造）。

V1 验收标准：

- 同样的上下文窗口下，回答对用户偏好命中率提升。  
- Prompt token 消耗显著低于全量注入。  
- 日志中不再出现原始隐私记忆文本。

## 10. 新增：账号绑定与跨设备记忆继承方案

### 10.1 结论（先定原则）

- 记忆系统应由后端主导，前端只上报对话与反馈信号。
- 记忆必须绑定“账号身份”，这样用户换手机、重装 App、跨端登录后可继承历史记忆。

### 10.2 `moe_no` 是否适合作为绑定键

可作为**对外稳定账号号段**，但不建议直接替代内部主键：

- 推荐内部仍以 `users.id`（主键）作为 `user_memories.user_id` 关联键（性能和一致性更好）。
- `moe_no` 作为用户可见账号标识，可用于排查、导出、客服定位、跨端识别。
- 若后续支持“按 moe_no 查询记忆”，在服务层做 `moe_no -> user_id` 映射后再读写记忆表。

### 10.3 跨设备记忆继承的最小落地

1. 登录后以 token 解析出的当前用户身份（映射到 `user_id`）读取记忆。  
2. 对话结束后异步提取记忆并写回同一 `user_id`。  
3. 新设备登录同账号时，走同一 `user_id`，自然读取到旧设备积累的记忆。  

### 10.4 对应你目标的意义

这套方案直接解决“Ollama 上下文有限、每次像重新开始”的问题：

- 上下文窗口负责“短期会话记忆”；
- 数据库存储负责“长期用户记忆”；
- 每轮由后端按相关性从数据库召回并注入，让 AI 在有限 token 下持续“记住这个人”。

## 11. Phase 2 拆解实现进度

> **2026-05-20 更新**：账号记忆「混合检索 + 设备分离 + OpenClaw 双层」已在 OpenClaw 文档落地；本节保留 2026-05-09 的 MVP 口径，勿与 [记忆系统-2026-05-20-变更整理.md](./记忆系统-2026-05-20-变更整理.md) 混淆。

### 11.1 当前目标（截至 2026-05-09，历史）

把“可用 Demo 记忆”升级为“账号绑定、可反馈、可演进”的用户级长期记忆系统：

1. **让 AI 记住同一个人**：跨会话、跨设备、跨天保持用户记忆连续性。  
2. **让记忆可治理**：记忆可查看、可纠正、可删除、可追溯。  
3. **让系统可学习**：基于用户反馈持续强化有效记忆、衰减错误记忆。  

### 11.2 已实现能力（后端 + 前端）

#### 后端已完成

1. 记忆注入优化（V1）：相关召回 + 注入预算 + 无命中回退 + 去重降噪 + 敏感日志收敛。  
2. 记忆元信息入库：`memory_type + confidence + source`。  
3. 冲突更新规则：已有人工记忆优先，低置信自动抽取不覆盖人工修订。  
4. 反馈闭环 V0：新增 `SubmitUserMemoryFeedback`（`accept/reject/correct`）并记录 `user_memory_feedback`。  
5. 用户级缓存：按 `user_id` 的短 TTL 内存缓存（命中读缓存，更新后失效），用于降低记忆读取延迟。  
6. 账号绑定策略落地：以 `users.id` 作为记忆主关联键，认证链路以 token 用户身份写入/读取。  

#### 前端已完成同步

1. 用户记忆模型已同步后端字段：`memory_type / confidence / source`。  
2. 记忆服务已接入反馈接口：`POST /api/user/:user_id/memories/feedback`。  
3. 记忆线页面已支持反馈交互：认可（accept）/驳回（reject）/纠正（correct）并回刷列表。  
4. 页面增加记忆元信息展示（类型、置信度），提升用户可见性与可审计性。  
5. 记忆管理面板新增“当前生效提示词预览”（可刷新、可复制、可展开），支持用户直接查看模型实际注入上下文。  
6. 记忆管理面板新增“注入策略配置”（注入模式 + 原始记忆注入条数上限），支持在配置侧直接调优小模型记忆注入行为。  
7. 聊天页已移除本地记忆注入/本地记忆抽取逻辑，改为统一由后端 `/api/llm/chat` 负责记忆注入与抽取。  
8. 聊天页“记忆库”入口已统一跳转到后端记忆线（`MemoryTimelinePage`），避免 Web/移动端出现双链路分歧。  
9. 记忆线页面新增“账号画像摘要（后端记忆聚合）”展示，确保画像来源可解释且跨端一致。  
10. `MemoryManagerPage` 已切换为后端记忆来源展示（运行状态 + 账号画像聚合 + 提示词注入预览），不再依赖本地 SQLite 作为主记忆源。  

### 11.3 正在进行（截至 2026-05-09）

1. 反馈数据到“强化/衰减任务”的离线策略实现（批处理调度与阈值参数）。  
2. 画像聚合任务“定时全量批处理”的补强（当前已支持写后异步刷新 + 读时过期重建，下一步补纯离线定时）。  

### 11.4 下一步（按优先级）

1. 基于反馈数据增加“强化/衰减”定时任务，形成可持续学习闭环。  
2. 补充关键指标看板：命中率、误提率、冲突率、注入成本、反馈采纳率。  
3. 画像聚合任务补齐“纯定时批处理”路径（与现有写后刷新/读时重建并存，进一步削峰）。  
4. 依据验收脚本做一轮 Web + Mobile 联合回归。  

### 11.5 里程碑判断标准

当满足以下条件，可认为“用户级记忆 MVP”达标：

1. 同用户多轮对话的偏好命中率稳定提升，且重复追问显著减少。  
2. 错误记忆可由用户纠正，且后续不会被低置信自动提取反复覆盖。  
3. 反馈数据能驱动记忆置信度与来源状态发生可观测变化。  
4. 核心链路可审计：能追溯记忆来源会话/消息与更新时间。  

### 11.6 性能与服务器压力口径（新增）

当前统一方案的性能控制策略：

1. 后端按 `user_id` 使用短 TTL 内存缓存，降低每轮对话直接打 DB 的频率。  
2. 记忆注入采用“相关召回 + 上限预算”，不会把全量记忆塞进模型上下文。  
3. 更新后主动失效缓存，保证数据一致性与命中效率平衡。  

已落地优化：

1. `GET /api/user/:user_id/memories` 已支持 `limit/offset` 分页，并返回 `total/has_more`。  
2. `user_memories` 增补复合索引（`user_id + updated_at`、`user_id + memory_type`）以提升高频查询性能。  
3. 记忆列表与画像查询新增慢查询日志口径（按耗时阈值输出 `cost_ms`、`limit/offset`、`rows/total`）。  
4. 画像查询改为“后端聚合缓存表”读取，支持写后异步刷新与读时过期重建，减少每次请求实时聚合开销。  

下一步性能优化建议：

1. 增加画像聚合的纯离线定时全量任务（按活跃用户窗口），进一步降低在线请求峰值。  
2. 细化慢查询观测到 Prometheus/日志平台（P95/P99 + SQL 指纹），建立告警阈值。  
3. 在注入策略上优先“画像摘要 + 少量高价值原始记忆”，继续压缩 token 成本。
