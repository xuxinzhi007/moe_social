| # | 决策 | 内容 |

| D1 | 英雄 AI 边界 | 英雄性格化对话 = **纯游戏内容**，不出现在星辉远征之外；不进 Companion Hub 聊天入口；Companion 深度陪伴地位不动 |
| D2 | Life 引擎转向 | 数字生命（`biz/life`）从「独立沙盒产品线」降级为 **Arena 英雄生活模拟内核**；僵尸运行状态终结 |
| D3 | 统一为「星辉活世界」 | 对话层（英雄会说话）+ 世界层（英雄在生活）+ 性格层（英雄有灵魂）合并实施，共享记忆与事件流 |

**一句话叙事**：用户在小家点开英雄能聊（今天聊昨晚世界里发生的事）；关掉 App，英雄还在全服共享的营地里过日子（训练、散步、闹别扭，还可能和其他用户的英雄作伴）；再打开时，世界已经往前走了。

## 3. 数据流闭环（本方案的核心价值）

```
世界 tick（低频）──产出──▶ life_event_logs（moments 事件流，唯一事实源）
                              │
              ┌───────────────┼────────────────┐
              ▼               ▼                ▼
        Hub「TA 的日常」   小家聊天上下文注入    英雄 per-hero 记忆
        （现有 moments）   （"昨晚下雨没睡好"）  （"你送过我三次花"）
              │               │                │
              └───── 用户互动（送礼/训练/聊天/喂食）反馈回世界数值 ─────┘
                        （mood/energy/好感 → 行为变化）
```

**合并的协同增益**（分开做则各自重复建设）：
1. **一条事件流两处消费**：Hub 展示与聊天注入共用 `life_event_logs`，不建第二套「英雄动态」
2. **一份性格两处生效**：角色卡同时喂 prompt（怎么说）和行为偏好表（怎么做）
3. **一套记忆一次建设**：per-hero 命名空间，世界事件与对话记忆同源
4. **边界护栏天然成立**：D1「不出游戏」使世界事件全部为游戏内语境，无现实话题泄漏风险

## 3.1 多用户状态模型（千人千面，同一个英雄）

> hero_id 是全局模板：同一个「小星」被所有用户拥有。多用户下必须分三层看待英雄的状态，
> **官方层与世界层共享，私人关系层私有**——世界是全服共同的舞台，关系只属于用户与英雄两个人。

| 层 | 归属 | 存什么 | 现有落点 | 共享范围 |
|----|------|--------|----------|----------|
| **官方人设层** | 全局共享 | 性格/背景/说话方式/世界观基调（角色卡 + 版本号） | 角色卡资产（内置官方卡） | **所有用户同一份**（保证「小星就是小星」） |
| **私人关系层** | （user_id, hero_id） | 羁绊/送礼记录/共同战斗史/聊天记忆（只存游戏内事实） | `CompanionMemory.UserID + MemoryKey` 扩展 hero 维度 | 仅该用户 |
| **世界实例层** | 全服共享（D4） | 营地 tick 演化、居民行为、世界事件 | `LifeWorld` 单实例（沿用现有 default 单世界引擎） | **所有用户同一份**（物理与事件共享） |

**三层如何合力达成目标**：
1. **一致性**来自官方层 —— 任何用户问小星「你是谁」，得到的性格内核相同；
2. **鲜活感**来自私人层 —— 我的小星记得我们的共同经历，你的小星记得你的；
3. **独特性**来自共享世界中的个人轨迹 —— 事件全服同源，但每名英雄的经历分岔（它和谁作伴、遇到什么、被你怎么照顾），聊天上下文自然不同。

**工程保证**：私人关系层落点已带 user 维度（表结构/索引），跨用户泄漏在结构上不成立；世界层共享的只有物理状态与事件，不含任何关系/记忆字段；M1 需补一条单测锁死「英雄记忆查询永不过用户边界」。

**共享与私有的边界（D4）**：共享的是**世界物理与事件**（地形/天气/灾害/英雄可见行为，全服同源一份）；私有的是**关系与记忆**（羁绊/聊天/游戏内事实，仍按（user_id, hero_id）隔离，K1 不变）；**不在范围**的是玩家实时联机与玩家级世界互动——异步共享 ≠ 多人联机，不违 D1 与 positioning 暂缓联机的边界。异地联机实验（game-network-lab）仅网络层，不涉及英雄记忆共享。

## 4. 关键设计决策

| # | 议题 | 决策 | 说明 |
|---|------|------|------|
| K1 | 记忆隔离 | 英雄记忆按 **（user_id, hero_id）二元组**命名空间，**只存游戏内事实** | hero_id 是全局模板 ID（同一英雄被所有用户拥有），仅按 hero_id 隔离会跨用户串数据；现有 `CompanionMemory.UserID` + `MemoryKey` 结构可直接扩展（如 `MemoryKey = hero:{heroID}:{key}` 或新增 scope 列）；账号级记忆（OpenClaw 库）**不进英雄**，英雄不知道用户的现实生活 |
| K2 | 性格落地 | `LifeEntity` 无性格字段 → 新增「性格→行为偏好」映射表（如 勤勉→训练频次↑、慵懒→睡眠时长↑） | 行为仍是需求驱动（hunger/energy），性格做加权偏好，不推翻现有 behavior.go |
| K3 | 成本护栏 | 聊天解锁挂羁绊等级（`bond ≥ 3`）；沉浸长文基调下单条回复设字数上限（建议 ≤300 字） | 英雄数量 × LLM 调用 × 长文是最大成本项（O2 定长文后权重上调）；羁绊门槛同时是养成目标；流式（SSE）在长文下体验收益大，M1 成本允许则优先流式 |
| K4 | 世界规模 | 共享世界人口治理：`MaxEntities` 上限保留，人口 = NPC 预算 + 全服入驻英雄；M1 单英雄期天然可控，M2 起需容量预案 | 共享世界人口既是内容也是成本项；扩容手段是**营地分区**（多个 `LifeWorld` 实例）而非私有化 |
| K5 | 存量数据 | 内测期**清档重开**（life_worlds/entities/logs 重建，居民由旧 Companion 猫猫换为英雄），重开后仍为单一共享世界 | 现存世界无人观看，数据无保留价值；绑定关系（决策 14）随清档重置；共享世界架构与引擎代码原样保留 |
| K6 | Companion moments | 清档过渡期 Hub「TA 的日常」允许空态兜底 | greeting/moodThought 独立数据源，不受影响 |
| K7 | 引擎包边界 | `biz/life` 保持独立包名与目录，Arena 通过接口消费 | 避免一次性大搬迁；命名在 M2 稳定后再议 |
| K8 | 官方卡版本化 | 角色卡全局共享、带版本号；记忆是事实（不可变），人设是基调（可迭代） | 卡更新后既有 per-user 记忆全部有效（“你送过我三次花”不因人设微调失效）；重大人设重构时首聊自然带过，不做记忆迁移 |
| K9 | 英雄间社交 | 共享世界内英雄间关系（social.go 亲和度）保留，成为聊天叙事素材（「今天和营地里那位剑士一起散步了」） | 异步社交雏形：玩家不同时在场，英雄替用户社交；展示层只用官方英雄名，不暴露用户身份 |

## 5. 分期路线

### M0 · 运维止血（待批准后执行，改动为硬编码字面量）
- `life_engine_enabled` 保持 true；`api_life.go` 中硬编码的 `TickInterval/FlushInterval` 5s → 5min
- D4 拍板后定性更新：现有单世界引擎**即目标架构**，降频 = 低功耗待机（不再是僵尸空转）；Companion moments 数据流不断供，M1 清档入驻无冷启动

### M1 · 单英雄 MVP（一个版本验证核心假设）
- **设计 1 名全新活世界旗舰英雄**（O3）：立绘 + 官方角色卡 + 行为偏好配置 + 基础数值，性格直接为「性格→行为偏好」映射表设计（示范标杆）
- 营地入口：**独立全屏世界页**（O1，复用 `LifeWorldPage` 全屏形态；进入共享世界，视角默认聚焦自己的英雄，他人英雄可见为营地居民）
- 范围：小家闲聊（沉浸长文，O2）+ 共享世界低频 tick + per-hero 记忆 + 登录快进摘要（O4，摘要只讲「你的英雄」在共享世界中的离线经历）
- 验证指标：解锁聊天用户的送礼/训练频次变化；聊天中世界事件引用的提及率

### M2 · 全 roster + 世界深度
- 三英雄全量入驻 + 性格→行为偏好全表 + 世界事件/道具/importance 分级（历史三大需求）
- 世界视图切换：Arena 小家页内嵌世界视图（与全屏页同一共享世界数据源，O1 的切换形态）；共享世界容量治理落地（K4 预案）
- `positioning` §2.1/2.2 文案正式更新

## 6. 明确不做（边界护栏）

- ❌ 英雄不出现在星辉远征之外的任何聊天入口（含 Companion Hub）
- ❌ 英雄不继承账号级记忆，不做现实话题
- ❌ 不做多角色陪伴回归（`companionSingleActiveBondPhase1` 决策不变）
- ❌ 不复活酒馆大厅；角色卡资产仅作为**人设格式**复用，入口不复用
- ❌ 不动 Companion 现有聊天链路与账号记忆链路

## 7. 已拍板决策（原开放问题，2026-09-02 全部关闭）

| # | 议题 | 决策 | 落地含义 |
|---|------|------|---------|
| O1 | 营地入口形态 | **默认独立全屏营地页**，支持切换 Arena 小家内嵌世界视图 | M1 先做全屏（复用 `LifeWorldPage` 本就是全屏形态，改造成本最低）；内嵌模式放 M2，两种视图共享同一世界数据源 |
| O2 | 对话风格基调 | **沉浸角色扮演（长文）** | token 成本高于吐槽风，K3 护栏同步上调（回复字数上限 ≤300 字）；长文下流式体验收益大，M1 优先评估 SSE |
| O3 | 首个英雄人选 | **为活世界设计全新英雄** | 不受现有三英雄人设束缚，性格直接为「性格→行为偏好」映射设计（旗舰示范）；代价是完整资产链：立绘 + 角色卡 + 行为偏好 + 数值 |
| O4 | 世界 tick 与登录 | **登录时快进摘要** | 离线不逐 tick 补算；按离线时长生成叙事化摘要事件（「你不在的 8 小时……」）写入事件流并注入聊天上下文——成本低，且与 O2 沉浸长文基调天然契合 |
