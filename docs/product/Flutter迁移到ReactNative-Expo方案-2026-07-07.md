# Flutter 迁移到 React Native + Expo 方案

## 1. 背景

当前项目的移动端基于 Flutter 开发，已经具备：

- 登录注册与基础业务页面
- 首页、成就页、我的页等产品页面
- 数字生命世界页
- 动效组件体系
- 现有后端 API / WebSocket 能力

随着产品继续演进，当前前端技术栈已经暴露出几个实际问题：

- 多端适配需要频繁单独调整
- 页面产品感和交互打磨成本偏高
- 调试链路相对繁琐
- 数字生命模块未来会从“页面功能”演进为“强交互世界模块”

因此需要评估是否迁移到更适合“产品化 App + 强交互模块”的技术方案。

## 2. 目标

本次迁移讨论的目标不是“为了换框架而换框架”，而是为了提升：

- 产品界面表达力
- 开发调试效率
- 设计系统落地效率
- Web / App 协同能力
- 数字生命世界模块的长期扩展性

## 3. 为什么考虑 React Native + Expo

## 3.1 适合当前项目形态

这个项目不是纯游戏，而是：

- 一个以移动端为主的产品 App
- 后端接口与业务逻辑已经独立
- 数字生命只是其中一个重要模块

对于这类项目，React Native + Expo 更适合承担：

- 移动端 UI 产品表达
- 页面快速迭代
- 动态样式和设计语言统一
- 与现有 React 后台团队思路衔接

## 3.2 与当前后台技术更接近

当前后台管理台已经使用 React。

迁移到 React Native 后，虽然不是直接复用 DOM 组件，但可以复用：

- React 思维模型
- 状态管理习惯
- 组件化方式
- TypeScript 工程体系
- 部分业务层设计经验

这会比继续维护 Flutter 和 React 两套前端生态更统一。

## 3.3 Expo 适合作为主工程底座

Expo 不是单纯“打包工具”，而是一整套开发与发布基础设施：

- 路由
- 调试
- 构建
- OTA 更新能力
- 常见原生能力接入
- Web 支持

对于个人项目或小团队来说，它能显著降低 React Native 的工程门槛。

## 4. Flutter 是否还能继续用

可以，但要分阶段判断。

## 4.1 短期可以继续

如果目标是：

- 先把数字生命玩法验证清楚
- 快速继续迭代当前版本
- 不想现在就开始大规模迁移

那么 Flutter 还可以继续承担当前版本开发。

## 4.2 中期如果要做成“产品”

如果目标是：

- 更强的产品感
- 更顺滑的 UI / 交互迭代
- 更好的 Web 协同
- 更强的前端生态复用

那么迁移到 React Native + Expo 会更合理。

## 5. Flutter 能嵌入吗

可以嵌入，但不推荐作为长期主方案。

## 5.1 Flutter 嵌入到原生 App

Flutter 官方支持把 Flutter Module 嵌入原生 Android / iOS App。

理论上可以采用：

- 主壳是原生 App
- 某个页面或某个功能使用 Flutter 渲染

## 5.2 Flutter 嵌入到 React Native

这条路理论上也能走，但工程复杂度会明显上升：

- React Native 与 Flutter 各自维护独立运行时
- 双端桥接、生命周期、路由切换会复杂
- 包体积会上升
- 调试链路会变得更重
- 长期维护成本高

所以结论是：

- **能嵌入**
- **不建议把 Flutter 作为 RN 主工程里的长期混合模块**

## 5.3 推荐做法

如果真的需要过渡期混合，推荐是：

- 不做“RN + Flutter 长期混编”
- 而是让 Flutter 继续维护旧版本
- 新版本直接在 React Native + Expo 上重建
- 后端接口复用，前端逐步替换

这比混合嵌入更稳。

## 6. 推荐迁移策略

推荐采用 **“后端不动，前端重建，分模块迁移”**。

不要试图：

- 直接自动转换 Dart 到 TypeScript
- 在 RN 里长期嵌 Flutter 页面
- 一次性全量迁完再测试

更合理的是：

1. 保持现有后端 API / WS 不动
2. 用 RN + Expo 新建移动端工程
3. 先迁公共基础设施
4. 再迁核心页面
5. 最后迁数字生命世界页

## 7. 建议的新前端架构

建议新工程采用：

- `React Native + Expo`
- `TypeScript`
- `expo-router`
- `zustand` 或 `redux toolkit`
- `react-query` / `tanstack query`
- `react-native-reanimated`
- `react-native-gesture-handler`
- `react-native-skia` 或 Canvas 方案用于世界渲染

## 7.1 页面层

- 首页
- 成就页
- 我的页
- 数字生命页
- 登录注册

## 7.2 基础设施层

- API Client
- WebSocket Client
- Config
- Auth
- Theme / Design Tokens
- Error Boundary / Loading / Empty States

## 7.3 世界模块层

数字生命页建议作为独立模块设计：

- `world-engine-view`
- `world-overlay`
- `world-control-panel`
- `world-event-timeline`
- `tribe-panel`

这样后面扩展到 WorldBox 风格时，不会和普通页面结构纠缠在一起。

## 8. 数字生命模块迁移建议

这是迁移中最特殊的部分。

## 8.1 不建议一比一照搬 Flutter 页面结构

应该把数字生命拆成三层：

- **模拟数据层**
  - REST / WS 状态同步
  - 世界摘要
  - 实体状态
  - 部落 / 聚落 / 生态区数据

- **渲染层**
  - 地图背景
  - 热区叠加
  - 连续移动插值
  - 实体精灵
  - 事件标记

- **交互层**
  - 上帝视角操作
  - 资源投放
  - 灾害触发
  - 观察模式切换

## 8.2 连续移动建议在迁移时一起改

既然要往 WorldBox 风格演进，就不要继续沿用当前“tick 一步一步跳”的表现方式。

迁移时建议直接切换为：

- 后端负责目标点、速度、状态
- 前端负责连续插值移动

这样 RN 版本能从一开始就比 Flutter 旧版更自然。

## 9. 迁移顺序建议

## 阶段一：基础工程

- 创建 Expo 工程
- 接入 TypeScript
- 接入路由、状态管理、API 层
- 接入设计 Token
- 建立构建与环境区分

## 阶段二：通用业务页面

优先迁移低风险页面：

- 登录注册
- 我的页
- 设置页
- 简单列表/详情页

原因：

- 验证基础工程是否稳定
- 建立 UI 组件库
- 降低一开始就迁复杂世界模块的风险

## 阶段三：首页与产品主线页面

- 首页
- 成就页
- 发现页 / 核心内容页

目标：

- 验证产品感和整体交互体验
- 建立新的视觉语言

## 阶段四：数字生命模块

最后迁移：

- 世界页
- 实体卡片
- 事件流
- 世界叠层
- 上帝干预面板

这一步建议按“新设计”来做，而不是机械照搬 Flutter 版。

## 10. 迁移成本评估

## 10.1 可以复用的东西

- 后端接口
- WebSocket 协议
- 配置分层思路
- 产品信息架构
- 设计规范
- 世界规则与后端模拟逻辑

## 10.2 不能直接复用的东西

- Flutter Widget
- Dart 页面实现
- Flutter 动效组件代码
- Flutter 布局适配代码

## 10.3 需要重写的东西

- 前端页面
- UI 组件库
- 动效实现
- 世界渲染层
- 移动端状态管理接入

## 11. 风险

## 11.1 最大风险

不是技术能不能做，而是迁移期容易出现：

- 两套客户端并行维护
- 接口协议频繁变动
- 页面体验“半新半旧”
- 数字生命模块迁到一半卡住

## 11.2 降低风险的方法

- 明确旧版 Flutter 只做保守维护
- 新版 RN 单独工程推进
- 后端协议尽量稳定
- 先迁简单页面，最后迁世界模块
- 数字生命按新设计重做，不做一比一复制

## 12. 最终建议

如果决定迁移，我建议采用下面这个结论：

- **不做 Flutter 嵌入 RN 的长期混合方案**
- **保留 Flutter 旧版作为过渡**
- **新建 React Native + Expo 工程**
- **以后端为稳定中台，前端逐步重建**
- **数字生命模块在 RN 中按 WorldBox 方向重做**

## 13. 对当前项目的明确结论

### 适合迁移吗

适合。

如果当前目标是继续验证数字生命玩法，可以先不立刻动迁移。

如果当前目标已经转向：

- 做成一个更成熟的产品
- 继续加强设计感
- 让数字生命变成核心展示功能

那么可以开始立项迁移。

能，但不推荐作为长期方案。

### 推荐方案

推荐：

- `React Native + Expo` 新建工程
- 后端复用
- Flutter 逐步退出
