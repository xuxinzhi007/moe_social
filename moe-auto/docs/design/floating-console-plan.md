# 悬浮控制台方案（可评审）

## 背景问题

- 当前主流程偏「整页配置」，跨 App 自动化时回看与干预成本高。
- 用户已开启无障碍后，状态反馈不稳定，导致“已授权但看起来不可用”。
- 运行中只有日志/通知，不够“随手控制”。

## 竞品交互抽样（用于设计参考）

- Auto.js / Hamibot 的常见模式：**悬浮球 + 展开控制台**（启动、停止、参数切换、状态文案）。
- Tasker Overlay Scene 常见模式：**小面积常驻 + 非阻塞覆盖**，尽量不打断前台 App。
- Android 安全限制：overlay 不能把已消费触摸“透传”给底层 App，交互区应尽量小且可收起。

## 我们的阶段化方案

### P0（本轮已落地）

- 修复无障碍授权识别逻辑（双通道检测，减少误判）。
- 运行时增加**悬浮状态条**（左上角，显示当前步骤进度）。
- 保留点击/滑动指示，不影响前台操作。

### P1（本轮已落地）

- 悬浮球（可拖动）+ 展开小面板
  - 停止
  - 打开主界面
  - 当前脚本与步骤
  - 收起
- 面板 8 秒自动折叠，保持小面积遮挡。
- 快速切换脚本（待下一步补齐）。

### P2（增强）

- 悬浮窗中内置“录制”入口（开始记录坐标/OCR/识图步骤）。
- 悬浮窗内快捷参数（延迟倍率、循环次数、异常策略）。

## 交互草图（预览）

```text
收起态（常驻）:
┌─────┐
│ Moe │  <- 可拖动，点开
└─────┘

展开态（运行中）:
┌─────────────────────────┐
│ 脚本: 签到流程            │
│ 步骤: 3/12 OCR 点击“发现” │
│ [暂停] [停止] [收起]      │
└─────────────────────────┘
```

## 技术边界

- Overlay 使用 `TYPE_APPLICATION_OVERLAY`，需悬浮窗权限。
- 交互区最小化，避免遮挡前台 App 关键按钮。
- 运行状态同步走 `AutoBridge` 单向流，不在 overlay 中做复杂业务逻辑。

## 可复用知识（沉淀）

1. 无障碍授权判断不能只依赖单一 API，需 `AccessibilityManager + Secure Settings` 双检。
2. 跨应用自动化的主反馈应优先放在 overlay，而不是仅在 App 内页面。
3. overlay 交互面积要小且可收起，避免遮挡目标 App。
4. 运行态文案更新应走单向桥接（`AutoBridge`），避免 UI 逻辑散落在执行器内。
